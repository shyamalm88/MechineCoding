Two Pointers

1. How to Spot This Pattern

1. Is the array/string SORTED (or can it be sorted without losing what you need)?
No → check steps 3-4 below (linked list / in-place signals).   Yes → continue.
2. Are you looking for a PAIR / TRIPLET / GROUP whose SUM, DIFFERENCE, or MIN/MAX COMPARISON hits a target?
Yes → Converging (opposite-direction) pointers: left at 0, right at n-1, move based on the comparison.   No → continue.
3. Is it a LINKED LIST, or do you need to find a CYCLE / MIDDLE / Nth-node-from-the-end?
Yes → Fast/Slow pointers (Floyd's): slow moves 1 step, fast moves 2.   No → continue.
4. Rearranging an array IN-PLACE (dedupe, partition into groups, merge into empty space)?
Yes → Same-direction read/write pointers, or a 3-pointer partition (Dutch flag).   No → probably not two-pointer - think hash maps or sliding window.
Signal
What's the single biggest giveaway for CONVERGING (opposite-direction) pointers?

A sorted array/string + "find a pair (or fixed-size group) whose sum/difference/comparison hits a target". Sorting turns SEARCH into DIRECTIONAL MOVEMENT:

  • If the current pair's value is too small, only moving left right can increase it - every value left of left is even smaller.
  • If it's too big, only moving right left can decrease it - every value right of right is even bigger.

Each move provably eliminates an entire row or column of impossible pairs - that's the O(N) speedup over checking every pair.

Signal
What's the giveaway for SAME-DIRECTION (fast/slow) pointers?

Two flavors - both "two pointers moving the same way, at different rates/roles":

  • Linked list: "detect a cycle", "find the middle", "Nth node from the end" → fast moves at 2x speed (or starts N nodes ahead).
  • Array, in-place: "remove/move/dedupe/partition without extra space" → slow = next write position, fast = scanner.

2. Core Idea & Template

Two-pointer problems split into a few families based on how the pointers move relative to each other: converging (start at opposite ends, move toward each other), fast/slow (race at different speeds), and same-direction (both start near the beginning, one runs ahead reading while the other writes).

Move the pointer that CAN'T possibly be part of a better answer.

let left = 0, right = arr.length - 1;

while (left < right) {
  const result = combine(arr[left], arr[right]);

  if (result === target) {
    // record / return - then move both inward
    left++;
    right--;
  } else if (result < target) {
    left++;  // need a bigger result
  } else {
    right--; // need a smaller result
  }
}

fast moves 2 steps, slow moves 1 - if there's a cycle, they're guaranteed to meet inside it.

let slow = head, fast = head;

while (fast && fast.next) {
  slow = slow.next;
  fast = fast.next.next;

  if (slow === fast) {
    // cycle found - phase 2: reset one pointer to head,
    // walk both 1 step at a time to find the cycle start
  }
}

slow = next write position, fast = scanner that decides what's worth keeping.

let slow = 0;

for (let fast = 0; fast < arr.length; fast++) {
  if (/* arr[fast] should be kept */) {
    [arr[slow], arr[fast]] = [arr[fast], arr[slow]]; // or arr[slow] = arr[fast]
    slow++;
  }
}
// arr[0..slow-1] is the result; slow is the new length

Dutch National Flag: partition into three buckets in one pass.

let low = 0, mid = 0, high = arr.length - 1;

while (mid <= high) {
  if (arr[mid] === A) {
    [arr[low], arr[mid]] = [arr[mid], arr[low]];
    low++; mid++;
  } else if (arr[mid] === B) {
    mid++;
  } else { // arr[mid] === C
    [arr[mid], arr[high]] = [arr[high], arr[mid]];
    high--; // don't advance mid - swapped-in value is unchecked
  }
}
Mnemonic: "Sorted + pair/triplet sum target → pointers converge from both ends. Linked list + cycle/middle → pointers race at different speeds. In-place rewrite → one pointer reads, one writes (or three pointers partition into buckets)."

3. Tricks & Twists

k-Sum: reduce to two pointers

Trick

Trigger words: "...triplet/quadruplet that sums to...", "find all unique combinations of k numbers that sum to target".

Sort first - then fix the first (k - 2) numbers with nested loops, and converge two pointers on the remaining pair (the base "two sum on a sorted array" case). Skip duplicates at every level - every fixed index AND both pointers - to avoid duplicate results.

Examples in this folder: 3Sum → 3SumClosest → 4Sum, each one rung higher on the same ladder.

Fill from the back

Trick

Trigger words: "merge into nums1 which has extra space at the end", "array is sorted by value but you need it sorted by something else (e.g. squares)".

When the destination has empty space at the end - or the final order is determined by comparing values from BOTH ends - iterate backward with multiple pointers, placing the largest remaining candidate into the last open slot. This avoids both an O(N log N) re-sort and overwriting data you still need.

Examples in this folder: mergeSortedArray, squaresOfSortedArray.

Greedy extremes pairing

Trick

Trigger words: "minimum number of boats/groups/pairs", "each group has at most 2 ... with a capacity limit".

Sort, then repeatedly try to pair the current SMALLEST remaining item with the current LARGEST. If they fit together, both are consumed; if not, the largest must go alone - nothing smaller could have helped it fit either. The largest always "uses up" one unit of capacity per iteration.

Example in this folder: boatsToSavePeople.

One mismatch, branch into two

Trick

Trigger words: "after deleting AT MOST ONE character/element", "can become valid by removing one item".

Run the normal converging check until the FIRST violation. At that point, don't give up - branch into two sub-checks, each skipping ONE side of the mismatch (left+1..right, or left..right-1). If either branch passes cleanly, the answer is true.

Example in this folder: validPalindromeII.

4. Common Pitfalls

Pitfall

while (left < right) vs <=: for a converging search over a PAIR, always use < - <= lets a pointer pair with itself. But fill-from-the-back merges (mergeSortedArray, squaresOfSortedArray) loop on REMAINING ELEMENTS (p2 >= 0, left <= right), not pointer-vs-pointer - read each problem's loop condition, don't copy-paste blindly.

Pitfall

k-Sum: forgetting to skip duplicates at every level (every fixed index, AND both left/right) → duplicate triplets/quadruplets in the output, even though every individual value found is correct.

Pitfall

Dutch National Flag (sortColors): incrementing mid after swapping with high - the value swapped IN from high hasn't been inspected yet and could itself need another swap. Only low-swaps are safe to pair with mid++.

Pitfall

Fast/slow on linked lists: checking only fast for null before doing fast.next.next crashes on odd-length lists, right when fast lands on the last node. Always check fast && fast.next together in the loop condition.

Story

twoSumII

Sorted array, looking for a pair that sums to target. Start with one pointer at each end - the smallest and largest possible values. If the pair sums too small, the only way to get bigger is to move left right (swap in a bigger "small" number). If it sums too big, move right left. Each move provably eliminates an entire row/column of impossible pairs - that's why two pointers beats checking every pair.

Family: The canonical converging two-pointer template - the base case every other pair/triplet/quadruplet problem reduces down to.

3Sum

Same target-sum hunt as twoSumII, but now for a TRIPLET that sums to 0. Fix one number with a loop (i) - the remaining two numbers must sum to -nums[i], exactly twoSumII on the rest of the array. Sort first so duplicates sit next to each other and can be skipped at all three levels (i, left, right) to avoid duplicate triplets.

Family: k-Sum reduction, step 1: 3Sum = fix one + twoSumII on the remainder. 3SumClosest and 4Sum extend this same ladder.

3SumClosest

Same skeleton as 3Sum - sort, fix i, converge left/right - but instead of hunting for an exact sum of 0, you're hunting for the sum CLOSEST to an arbitrary target. Track the best (smallest |sum - target|) seen so far; move left right when the sum is too small, right left when too big, and short-circuit the moment you hit an exact match (can't get any closer).

Family: k-Sum reduction, same family as 3Sum - swaps "find exact 0" for "minimize distance to target"; sort, converge, and the outer fixed index all stay identical.

4Sum

One rung higher on the same ladder: fix TWO numbers with nested loops (i, j), then converge left/right on the remaining pair - the same twoSumII core, just called from one level deeper. Skip duplicates at all FOUR levels (i, j, left, right) to avoid duplicate quadruplets.

Family: k-Sum reduction, step 2: 4Sum = fix two + twoSumII on the remainder. The pattern generalizes - kSum = fix (k-2) numbers with nested loops, then twoSumII on what's left.

Story

containerWithMostWater

Two walls, water level capped by the SHORTER one. Start with the widest possible container (both ends). At each step, area = min(height[left], height[right]) * width. The wall that's currently shorter is the bottleneck - moving it MIGHT find something taller and increase the area. Moving the TALLER wall can only shrink the width while the height cap stays the same (still limited by the short wall) - so it can never help. Always step the shorter wall inward.

Family: Converging pointers with a GREEDY ELIMINATION move rule based on which side is the current bottleneck - not a sum comparison. trappingRainWater extends this same "shorter side is the bottleneck" idea to compute trapped water at every position.

Story

trappingRainWater

Extends containerWithMostWater's bottleneck idea: instead of one area, sum up trapped water at EVERY index. Track running leftMax/rightMax as you converge. Whichever side is currently shorter (height[left] < height[right]) is GUARANTEED to have its water level capped by its OWN running max - because the other side's max is provably even taller. Process that side: either it's a new max (no water on a peak) or water = runningMax - height[i].

Family: Converging pointers + "shorter side is bounded by its own max" - the direct generalization of containerWithMostWater from "one container's area" to "water trapped above every bar".

Story

boatsToSavePeople

Sort by weight, then greedily pair the HEAVIEST remaining person with the LIGHTEST. The heaviest person is going on a boat no matter what - the only question is whether anyone can join them, and the lightest person is their best (and easiest-to-check) chance of fitting. If they fit together, both leave; either way, the heaviest always consumes one boat.

Family: Greedy converging pointers - "pair the extremes" - sort first so the two pointers represent "currently lightest unassigned" and "currently heaviest unassigned".

Story

squaresOfSortedArray

The array is sorted by VALUE, but squaring un-sorts it - the biggest squares come from whichever end has the largest ABSOLUTE value (very negative or very positive). Compare |nums[left]| vs |nums[right]|; the bigger one's square is the LARGEST remaining square overall, so it goes into the LAST open slot of the result, working backward.

Family: Fill-from-the-back - converging pointers compare a derived quantity (absolute value) and place the winner into a result array built from the end inward. mergeSortedArray uses the same back-to-front fill, comparing raw values instead.

validPalindromeII

Standard converging palindrome check - until the FIRST mismatch. You're allowed to delete exactly ONE character, so don't give up: branch into two sub-checks - "is s[left+1..right] a palindrome?" OR "is s[left..right-1] a palindrome?" (skip one side or the other). If either branch is a clean palindrome, the answer is true.

Family: Converging pointers + "one allowed exception, branch both ways" - useful whenever a problem says "...after removing/changing AT MOST ONE element".

Story

moveZeros

slow marks the next position where a non-zero value belongs; fast scans every element. Whenever fast finds a non-zero, swap it into slow's slot and advance slow. Zeros never get explicitly "moved" - they just get swapped further and further right as non-zeros leapfrog past them, naturally settling at the end.

Family: Same-direction read/write pointers - slow = write head, fast = scanner. removeDuplicatesII and sortColors are the same idea with a different "should I keep this?" rule.

Story

removeDuplicatesII

insertIndex is the write head - it only ever points at valid, deduplicated output. For each i, the question is: "would writing nums[i] make THREE in a row?" Check nums[i] !== nums[insertIndex - 2] - if the value 2 slots back in the OUTPUT differs, this value hasn't appeared twice yet in the result, so it's safe to write.

Family: Same-direction read/write pointers - the "keep at most 2 of each" rule is just a comparison against a fixed offset behind the write pointer. moveZeros is the simplest version of this family (keep rule = non-zero); this adds a "lookback" condition.

Story

sortColors

Three pointers partition the array into [0s | 1s | 2s] in one pass - the Dutch National Flag. low/high are the boundaries of the known-0 and known-2 regions; mid is the cursor. A 0 swaps to the front and BOTH low and mid advance (the swapped-in value is already known-good - it was either a processed 1 or the old low). A 2 swaps to the back, but high only shrinks - mid STAYS, because the value swapped in from high is unknown and must still be inspected. A 1 is already home; just advance mid.

Family: Three-pointer in-place partition - the natural extension of moveZeros'/removeDuplicatesII's read/write idea to THREE buckets instead of two, with the extra twist that one pointer (high) moves toward mid instead of away from it.

Story

mergeSortedArray

nums1 has empty space at the END - exactly enough for the merged result. Three pointers: p1/p2 scan the valid tails of nums1/nums2 from the back, p writes from the back of nums1. At each step, whichever tail is currently LARGER gets copied into the last open slot - guaranteeing the result ends up sorted without ever overwriting a nums1 value you still need to compare.

Family: Fill-from-the-back - same idea as squaresOfSortedArray (place the current "winner" into the last open slot, walk pointers inward/backward), but merging two separate arrays instead of re-deriving order from one.

backspaceStringCompare

Backspaces only ever delete characters to their LEFT, so the only safe direction to compare is RIGHT TO LEFT. Two pointers start at the END of each string. getNext walks a pointer leftward, counting pending # as "skip the next real character". Once both pointers land on a real (non-skipped) character, compare them - a mismatch (or one string running out before the other) means false.

Family: Converging-from-the-end pointers on TWO sequences - instead of meeting in the middle, both walk leftward in lockstep, each pre-processing its own "skip list" as it goes.

Story

partitionLabels

Not a classic two-pointer search - but the SAME "expand a window, then cut" shape as sliding window. Precompute each character's LAST occurrence. Walk left to right, growing end = max(end, lastIndex[char]). The instant i === end, every character seen so far is GUARANTEED to not reappear later (its last occurrence is already inside the window) - cut here and start a new partition.

Family: Greedy window-extension via a "last occurrence" map - distinct from converging/fast-slow two-pointer, but answers a similar "where can I safely cut this sequence" question. Worth knowing alongside true two-pointer patterns because it's commonly grouped with them.

Story

linkedListCycleII

Floyd's Tortoise and Hare. slow moves 1 step, fast moves 2. If the list has NO cycle, fast simply runs off the end (fast.next becomes null) first. If there IS a cycle, fast laps slow and they MEET inside the loop. The meeting point isn't the cycle start - but a bit of math (a = c, where a = head→cycle-start and c = meeting-point→cycle-start) shows that resetting one pointer to head and walking BOTH 1 step at a time makes them meet exactly at the cycle's start.

Family: Fast/slow pointers on a LINKED LIST - the only sub-pattern in this folder where the pointers race at DIFFERENT SPEEDS rather than converging or scanning together. The same 1x/2x trick also finds the middle of a list (LC 876) and detects whether a cycle exists at all (LC 141).
